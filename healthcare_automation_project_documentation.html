PROJECT DOCUMENTATION

Healthcare Management System Automation Framework

Java · Selenium WebDriver · Cucumber BDD · JUnit · Maven · Jenkins · GitHub

End-to-end UI automation and continuous integration project

1. Project Overview

The Healthcare Management System Automation Framework is an end-to-end UI test automation project for important workflows in a healthcare management application. It uses Java and Selenium WebDriver for browser automation, Cucumber BDD for readable scenarios, JUnit for test execution, and Maven for build and dependency management.

Jenkins is integrated with the GitHub repository. A code change was pushed and a new Jenkins build was observed. The test target is a locally hosted healthcare demo application called CarePoint.

Objectives

  • Automate healthcare application workflows.
  • Validate authentication and user access.
  • Test patient registration and appointment management.
  • Build reusable automation components.
  • Generate readable test reports.
  • Integrate test execution with CI.

3. Project Architecture

The framework follows a layered structure based on the Page Object Model (POM).

  • Feature layer: human-readable Cucumber scenarios.
  • Step definition layer: connects Gherkin steps to Java methods.
  • Page object layer: page-specific locators and browser interactions.
  • Driver layer: manages Selenium WebDriver creation and configuration.
  • Hooks layer: setup and cleanup around scenarios.
  • Configuration layer: application and test configuration.
  • Reporting layer: Cucumber HTML, JSON and XML reports.
  • CI layer: Jenkins executes Maven tests and publishes reports.

Execution flow

GitHub push → webhook/SCM trigger → Jenkins → Maven → JUnit/Cucumber → Selenium WebDriver → CarePoint → test results → reports → Jenkins artifacts.

6. Page Object Model

The framework separates page-specific browser interactions from test scenarios.

  • LoginPage.java — login page actions and elements.
  • DashboardPage.java — dashboard interactions.
  • PatientsPage.java — patient management interactions.
  • AppointmentsPage.java — appointment management interactions.
  • BasePage.java — common page-level functionality.

Benefits include reduced duplicated Selenium code, separation of locators from workflows, easier maintenance, improved readability and support for additional workflows.

7. Cucumber BDD

Cucumber allows test scenarios to be written in Gherkin syntax. Java step definitions connect the readable steps to Selenium operations.

Feature: Healthcare user authentication

  Scenario: Admin logs in successfully
    Given the user opens the healthcare application
    When the admin enters valid credentials
    And the admin clicks the login button
    Then the admin should see the dashboard

Benefits include readable scenarios, separation of business behaviour from implementation, and improved test documentation.

8. Maven and Local Application

Maven manages dependencies and test execution. The project uses Selenium Java 4.25.0, Cucumber 7.20.1, Cucumber JUnit 7.20.1 and JUnit 4.13.2.

Run tests locally

mvn clean test

Start the local CarePoint demo application

python -m http.server 8080 --directory app/demo

Application URL: http://localhost:8080. Keep the local server running in a separate terminal while executing Selenium tests.

9. Jenkins CI Integration

A Jenkins Freestyle job named Healthcare-Automation-Framework was configured. Jenkins is available locally at http://localhost:8081.

  • Configured Java 21 as the Jenkins runtime.
  • Configured Maven as a Jenkins build tool.
  • Configured a Windows batch build step to run mvn clean test.
  • Copied generated reports into the Jenkins workspace.
  • Configured HTML Publisher to publish the report.

HTML Publisher configuration

SettingValue
HTML directory to archivereports
Index pageindex.html
Report titleHealthcare Cucumber Test Report

Troubleshooting achievement

Cucumber reports were initially generated in the local project directory while HTML Publisher searched in the Jenkins workspace. This caused publishing to fail despite successful test execution. The build script was updated to copy HTML, JSON and XML reports into %WORKSPACE%\reports before publishing. This resolved the directory mismatch.

10. Cucumber Reporting

The Cucumber runner generates console output and HTML, JSON and JUnit XML reports.

plugin = { "pretty", "html:reports/cucumber.html", "json:reports/cucumber.json", "junit:reports/cucumber.xml" }
  • HTML: human-readable scenario and feature results.
  • JSON: structured results for downstream reporting integrations.
  • XML: JUnit-compatible results for CI integrations.

The HTML report is copied to index.html in the Jenkins workspace for publication.

Jenkins was configured with the repository URL, branch specifier */main, and GitHub hook trigger for GITScm polling. A README change was committed and pushed; a new Jenkins build appeared without manually selecting Build Now.

Verification caveat: the GitHub webhook page previously displayed a connection warning for a placeholder public URL. The observed automatic build confirms that a trigger path worked, but the exact webhook delivery configuration should still be checked before claiming every delivery is successful.

12. What Makes This Implementation Stand Out?

Project-specific differentiators

  • Healthcare-oriented workflows rather than only a generic login demonstration.
  • A locally hosted CarePoint demo application used as a controllable test target.
  • Separate Java runtimes: Java 17 for the test project and Java 21 for Jenkins.
  • A practical Jenkins workspace/report-directory mismatch diagnosed and fixed by copying report files before publication.
  • An integrated GitHub-to-Jenkins workflow where a repository change was followed by a new Jenkins build.
  • Multiple report formats—HTML, JSON and XML—from the same Cucumber execution.
  • Separate local ports: CarePoint on 8080 and Jenkins on 8081.

These are implementation differentiators, not claims that the underlying technologies or techniques are globally unique. The value is in combining and troubleshooting them into a working project.

13. Known Limitations and Accuracy Notes

  • The target is a local demo application, not a real healthcare provider system.
  • The current suite contains six scenarios and should be expanded.
  • The local application server must be running for UI tests.
  • The Jenkins job currently depends on a local project directory.
  • The webhook delivery configuration should be verified.
  • The .github/workflows/ui-tests.yml file exists, but a successful GitHub Actions execution has not been established.
  • No production patient data or real medical records are involved.
  • Production security, performance, accessibility and API testing have not been established as implemented.
